# スマホ位置情報とSpeedtestの一括取得

## 状態

`completed`

PC側の実装・自動テストと、利用者によるWindows・iPhoneでの正常系の実機確認が完了したため `completed` とする。未確認の異常系は検証記録に明記する。

## 目的

PC上で一つのコマンドを実行し、スマホからの位置情報受信と公式Ookla Speedtest CLIによる通信性能の取得を連続して行う。両方が成功した場合に、一回分の取得結果をまとめてターミナルへ表示し、自動終了する。

「一本のスクリプト」は利用者が実行する入口を一つにする意味とする。HTTP処理、トンネル管理、Speedtestの取得処理を一ファイルに集約したり、既存コードをコピーしたりしない。

## 前提と現在の実装

- 計画の基準はGitHubの `main`、コミット `6deab4c`。
- `scripts/phone_location_probe.py` はHTTPサーバーとトンネルを自動起動し、Ctrl+Cまで位置情報を繰り返し受信・表示する。
- 同ファイルの `Handler` と `validate_location` がトークン照合、JSON解析、座標の変換・検証、UTC変換、PCの受信時刻付与を担当している。
- `scripts/cloudflare_tunnel.py` の `run_tunnel(token)` はQR表示と子プロセスの監視を行い、現在はCtrl+Cまたは異常終了まで戻らない。
- `src/speedtest.py` の `run_speedtest()` は公式CLIを一回実行し、必要な生値だけを辞書として返す。失敗時は `RuntimeError` を送出する。タイムアウトは180秒。
- `scripts/speedtest_probe.py` はその結果を単独表示する。
- `src/location.py` と `scripts/location_probe.py` はWindows本体の測位用として残っているが、今回の機能では使用せず、フォールバックにも使わない。
- 位置情報の取得元はスマホとする。既存のiPhoneショートカットと送信JSONの仕様は変更しない。

## 今回の範囲と提案する決定事項

以下を本計画の提案仕様とする。`approved` への変更は、これらの方針の承認も意味する。

| 項目               | 今回の仕様                                                                        |
| ------------------ | --------------------------------------------------------------------------------- |
| 起動コマンド       | `scripts/measurement_probe.py` を新設する                                         |
| 取得順             | 位置情報を一件受信した後にSpeedtestを一回実行する                                 |
| 終了条件           | 両方の取得後に結果を一度表示して終了する                                          |
| 再試行             | Speedtestの自動再試行は行わない。不正な位置情報は拒否し、期限内の正しい再送を待つ |
| 位置情報の受信待ち | QR表示完了から180秒。トンネルの公開URL取得待ち60秒とは別に扱う                    |
| 重複受信           | 最初に受理した有効な位置情報だけを採用し、以後の有効なPOSTはHTTP 409で拒否する    |
| トンネル           | 結果取得中も維持し、正常終了・失敗・中断時に停止する                              |
| 結果               | `location` と `speedtest` を含むJSONをターミナルへ一度表示する                    |
| 保存               | ファイル・SQLiteともに保存しない                                                  |

今回の「ネットワーク情報」は既存のSpeedtestによる通信性能・サーバー情報を指す。SSID、BSSID、信号強度、チャネル、周波数・帯域の取得は別機能とする。

屋内外、場所名、階数等の入力、SQLiteの設計・保存、試行回数の永続化、集計、繰り返し計測、サーバー固定、スマホの継続追跡も対象外とする。今回は要件をすべて満たす保存用の完成計測レコードではなく、取得処理を結合する試作である。位置情報だけの受信やSpeedtest失敗を、成功した計測として扱わない。

README.md、既存計画書、依存関係は変更しない。Windows測位コードの削除は、本機能の実装とは分けた整理作業とし、今回の変更に含めない。

## 利用者が確認する動作

プロジェクトのルートから、プロジェクトの仮想環境で実行する。

```powershell
.\.venv\Scripts\python.exe scripts\measurement_probe.py
```

1. PCが127.0.0.1:8765でHTTPサーバーを起動し、起動ごとのトークンを作成する。
2. Cloudflare Tunnelを自動起動し、トークン付き送信先URLとQRコードを同じターミナルへ表示する。
3. PCは「位置情報を待っています」「送信後もSpeedtest完了まで同じ場所に留まってください」と分かる案内を表示する。
4. 利用者が既存のiPhoneショートカットを起動し、QRを読み取り、現在地を送信する。
5. iPhoneには従来どおり `{"status": "ok"}` を返す。この応答は位置情報の受理を表し、Speedtest完了を表さない。
6. PCは位置情報の受理とSpeedtestの開始を案内し、公式CLIを一回実行する。スマホへのHTTP応答をSpeedtest終了まで待たせない。
7. PCに位置情報とSpeedtestの結果をまとめたJSONが一度表示される。位置情報単独のJSONはこのモードでは表示しない。
8. PCが受信サーバー、トンネル、関連スレッドを片付けて終了する。正常取得時の終了コードは0。

別ターミナルの起動、トークンの転記、URLの手入力、終了のためのCtrl+Cは正常系では不要。任意の段階でCtrl+Cによる中断も可能にする。スマホ側の作成・操作は利用者が担当し、専用の手順書やWebページは追加しない。

## データと出力仕様

### スマホからの入力

POST先は既存どおり `/location?token=...`、Content-Typeは `application/json`。

```json
{
    "latitude": "40.42",
    "longitude": "-86.91",
    "sent_at": "2026-11-04T12:00:00Z"
}
```

既存の変換・検証・HTTPエラー仕様を維持する。`received_at` はPCで付与し、クライアントが送った同名フィールドは信用しない。緯度・経度は数値文字列またはJSON数値を受け付け、floatへ変換する。日時はUTCへ正規化する。精度フィールドは追加しない。

`sent_at` はスマホが生成した送信準備時刻であり、GPSの測位時刻を保証しない。今回は端末時計のずれや位置情報の鮮度を理由とする追加拒否条件を設けず、既存仕様を維持する。PCの `received_at` とSpeedtestの `timestamp` を分けて保持し、同時取得したかのように時刻を書き換えない。

### 統合結果

トップレベルのキーは `location` と `speedtest` の二つとする。

- `location` は `latitude`、`longitude`、`sent_at`、`received_at` の四項目。
- `speedtest` は `run_speedtest()` が返した辞書をそのまま格納する。`timestamp`、`ping`、`download`、`upload`、`packetLoss`、`server` と、それぞれの既存の下位項目を維持する。
- Speedtestの生値・単位を変換しない。既存の欠損値 `None` はJSONの `null` とする。
- ISP、IPアドレス、インターフェース、結果URL・ID、セッショントークンを統合結果へ追加しない。
- `json.dumps(..., indent=2, allow_nan=False)` で表示する。JSON化できない場合は成功出力を行わずエラーにする。整形は全体を文字列化してから一度の出力で行う。
- 案内・QRも同じターミナルへ表示するため、コマンドの全出力を一つのJSONとして扱う仕様にはしない。

統合JSONの検査では、Speedtestの全フィールドが返り値と一致することを比較する。架空の成功値や0で欠損を埋めない。試行回数を表示する機能は今回追加せず、Speedtestの呼び出し回数が一回であることをテストする。

## 実装設計

### 入口と責務

`scripts/measurement_probe.py` に `main()` を新設する。起動時のプロジェクトルートの解決は既存の `speedtest_probe.py` と同じ方式とし、別の作業ディレクトリから絶対パスで起動してもimportできるようにする。

取得全体の制御はこの入口に置く。HTTPの解析・検証、トンネルの管理、Speedtestの取得は既存処理を呼び出す。取得のために既存のprobeスクリプトを子Pythonプロセスとして起動し、その標準出力を解析する構成にはしない。

### 位置情報の受け渡し

既存の `Handler` に、サーバー側に設定した任意の `on_location(data)` コールバックを呼び出せる経路を追加する。

- コールバック未設定時は従来どおり受信データを表示してHTTP 200を返す。既存の位置情報単独コマンドは連続受信を維持する。
- コールバック設定時は、既存の全検証と `received_at` の付与が終わったデータを渡す。受信データ単独の表示はしない。
- コールバックは短時間で受理可否を返し、HTTPハンドラーからSpeedtestを呼び出さない。
- 新しい入口のコールバックはLockで受理状態を保護する。受付中かつ未受理なら最初の一件を採用して `True`、受理済み・期限終了・中断中なら `False` を返す。
- `True` の場合はHTTP 200と既存の成功応答、`False` の場合はHTTP 409と `{"error": "Location is no longer being accepted."}` を返す。
- 同時POSTでも採用は一件だけとする。二件目で採用済みの座標・日時を上書きしない。
- 不正入力は既存の400等を返し、採用状態を消費しない。期限内であれば正しい再送を受け付ける。
- HTTP応答の送信を試みた後にメイン処理へ受理完了を通知する。検証済みデータを採用した後にクライアントが切断しても、採用の取り消しや二重取得は行わない。応答送信の失敗を記録し、送信待ちがSpeedtest終了まで続かないようにする。
- 完了通知には任意のサーバー属性 `on_location_responded()` を用いる。新しい入口がEventを設定する関数を渡し、Handlerは採用した一件についてのみ、成功応答の送信処理のfinallyから呼ぶ。未設定時は何もしない。受理用コールバックと通知用コールバックの二つに責務を限定する。
- 採用判断後の応答失敗でもメイン処理へ通知するようfinallyを使用する。ハンドラー内から `server.shutdown()` は呼ばない。

### トンネルの停止と起動完了通知

`run_tunnel(token, *, stop_event=None, on_ready=None)` の形で任意の連携引数を追加する。既存の `run_tunnel(token)` と単体CLIはそのまま利用できるようにする。

- `stop_event` が設定されたら監視ループを抜け、既存のfinallyでcloudflaredを停止して正常な停止として0を返す。0.2秒程度の既存のポーリングを利用し、停止要求を長時間待たせない。
- `on_ready` はURLとQRの出力が完了した時点で一度だけ呼ぶ。これはQR表示の準備完了通知であり、Cloudflareの外部接続が確立した保証ではない。
- 未導入、公開URL取得60秒超過、予期しない子プロセス終了は従来どおり失敗とする。
- 新しい入口はトンネルをワーカースレッドで呼び出す。戻り値または例外をQueue等で必ずメイン処理へ通知する。ワーカーの例外を握り潰して受信待ちを続けない。
- 正常終了・例外・停止要求で、出力読取スレッド、パイプ、子プロセスを片付ける。停止に応じないcloudflaredは既存の5秒待機後のkillを使用する。

### 全体の制御と失敗時の扱い

1. ポート確保後にHTTP受信スレッドを起動し、その後トンネルを起動する。ポート確保に失敗したらトンネルもSpeedtestも起動しない。
2. QR表示完了通知後に、180秒の受信待ち期限を設定する。早期に有効なPOSTを受理済みなら待ち直さず次へ進む。
3. 受信待ち中は位置情報、トンネルの終了・例外、期限、中断を監視する。長いsleepや無期限のjoinでメイン処理を止めない。
4. 期限と受信の競合は同じLockで受付状態を確定する。期限以降の未採用データは拒否し、Speedtestを開始しない。
5. 最初の有効データを採用し、HTTP応答処理の完了通知後にSpeedtestを一回だけメインスレッドで呼ぶ。
6. 有効データを採用する前のトンネル異常終了は全体の失敗とする。採用後のトンネル異常終了は警告を表示するが、受信済みデータは破棄せずSpeedtestの取得を続ける。位置情報の再送は必要ないためである。
7. 両方の取得が成功したら統合JSONを表示する。Speedtestが失敗したら統合JSONは表示しない。位置情報だけを成功結果として代用しない。
8. すべての経路でfinallyから受付を閉じ、トンネルへ停止要求を送り、サーバーをshutdown・closeし、開始済みスレッドをjoinする。開始していないスレッドはjoinしない。`shutdown()` は `serve_forever()` が稼働している場合に限り別スレッドから呼ぶ。
9. 受信中の接続には既存の15秒のタイムアウトがある。新規受付を閉じたうえで処理中ハンドラーも終了させ、終了後のポート再利用を確認する。daemon化だけで後片付け済みと扱わない。

| 状況                                         | 利用者に見える結果                                     | 終了コード |
| -------------------------------------------- | ------------------------------------------------------ | ---------- |
| 両方成功                                     | 統合JSONを一度表示し、自動終了                         | 0          |
| 不正なPOST                                   | スマホへ既存のHTTPエラー。PCは期限内の有効なPOSTを待つ | 継続       |
| 有効データの二重送信                         | 後続のPOSTへ409。Speedtestは追加実行しない             | 継続       |
| 受信待ち180秒超過                            | 位置情報待ちタイムアウトを表示。Speedtestは実行しない  | 1          |
| ポート使用中・起動失敗・受理前のトンネル終了 | 原因を表示し、成功結果を出さず終了                     | 1          |
| Speedtest未導入・失敗・180秒超過・不正な結果 | 既存の原因を表示し、統合JSONを出さず終了               | 1          |
| 結果のJSON化・後片付けの失敗                 | 原因を表示し、成功終了としない                         | 1          |
| Ctrl+C                                       | 中断を表示し、成功結果を出さず後片付けして終了         | 130        |

通常のエラーは標準エラー出力へ表示し、予想される失敗で不要なトレースバックを出さない。トークン付きURLをHTTPアクセスログや統合結果へ出力しない。QR表示のための送信先URL表示は従来どおりとする。

Speedtest実行中のCtrl+Cも対象とする。既存のsubprocess管理が中断時に終了することを確認し、必要な場合に限って `src/speedtest.py` の終了処理を修正する。生値の抽出・CLIオプション・180秒の上限は変更しない。

## 実装するテスト

### 全体制御：tests/test_measurement_probe.py

- モックした有効な位置情報とSpeedtest結果で、`location` と `speedtest` が完全一致する統合JSONを一度だけ出す。元の辞書を変更しない。
- 位置情報受理前はSpeedtestを呼ばず、応答完了の通知後に一回だけ呼ぶ。
- 二件の同時POSTでも受理は一件、Speedtestも一回。二件目は409で採用結果を上書きしない。
- 不正なPOSTの後でも、期限内の正しいPOSTで成功できる。
- QR表示前には受信待ち期限を開始せず、表示後に180秒で終了する。境界の採用・期限競合も確認する。
- 受信待ちタイムアウト、ポート確保失敗、トンネル起動失敗・例外・受理前終了でSpeedtestも統合JSON出力も行わない。
- 受理後のトンネル終了では警告を出し、Speedtestの成功時には統合結果を表示できる。
- SpeedtestのRuntimeError、JSON化失敗、Ctrl+Cで成功結果を出さず、終了コードが仕様どおりになる。
- 受信待ち中とSpeedtest実行中の中断、途中までの起動失敗、正常終了の各経路で停止Event設定、serverのshutdown・close、スレッドjoinが行われる。
- ローカルHTTPサーバーへの実際のPOSTとモックしたトンネル・Speedtestを組み合わせ、HTTP応答、統合表示、終了後のポート再利用を確認する。

### HTTP受信：tests/test_phone_location_probe.py

- コールバック未設定時の既存の連続受信・表示とHTTP 200が変わらない。
- コールバック設定時に、検証済み四項目だけを渡す。成功時の単独JSON表示を抑制する。
- 不正なJSON・座標・日時・トークンではコールバックを呼ばない。
- コールバックがFalseを返す場合は指定した409を返す。
- HTTP応答完了後に通知する。応答時のBrokenPipeError等でも通知と後片付けが失われず、採用を取り消さない。
- 既存の座標変換、非有限値拒否、UTC変換、Content-Type、サイズ上限、タイムアウト、トークン非記録の仕様を維持する。

### トンネル：tests/test_cloudflare_tunnel.py

- 引数を省略した既存API・CLIの動作を維持する。
- QR出力完了後にon_readyを一度呼び、失敗前には呼ばない。
- 停止Eventを起動前・URL待ち中・表示後に設定しても、子プロセスと読取スレッドを片付けて戻る。
- 未導入、公開URL取得60秒超過、子プロセス異常終了、on_readyの例外で後片付けが行われる。
- 終了待ち5秒を超える子プロセスをkillする既存テストを維持する。

### Speedtest：tests/test_speedtest.py

- subprocessをモックし、要求する生値・単位・欠損値が変更されず返ることを実際の返却構造に対して検証する。
- ISP、IP、interface、結果URL・IDを含む入力でも返却結果に含めない。
- 未導入、非ゼロ終了、タイムアウト、不正JSON、未完了resultの各エラーを検証する。
