# Webページからの場所情報入力と計測結果への追加

## 状態

`completed`

場所情報の入力・検証・出力と自動テストが完了。利用者による一括取得・単独受信の動作確認と完了指示に基づきcompletedとする。本機能の完成条件と検証結果は本書で管理する。

## 目的と今回の範囲

スマホのWebページから、座標に加えて屋内外・場所名・詳細位置を入力してPCへ送信し、一回の計測結果としてPCのターミナルに表示する。

位置情報の取得は、ショートカット方式を廃止した現在のWeb方式だけを対象とする。場所情報はすべての位置情報POSTで必須にし、旧形式との互換性分岐は設けない。

今回の機能は、現在の一回分の入力と受信・出力だけに限定する。入力履歴の保存、前回値の復元、登録済み場所の選択、建物・階数一覧、SQLite、ファイル出力、地図、住所の自動補完、計測の再試行は追加しない。最終結果をスマホへ表示する機能も追加しない。

今回の計画書更新では本ファイルだけを変更する。既存コード、README.md、他の計画書、設定ファイルは読み取り専用とする。以下のコード変更は実装担当が行う作業を示す。

## 現状

- 基準：ローカルの `786f81b`（画面表記の大文字小文字を整理したコミット）時点の実装。
- `scripts/measurement_probe.py` と `scripts/phone_location_probe.py` は引数なしでWeb方式を起動する。`--location-method` は削除済みで、指定すると起動前に引数エラーとなる。

- 現在、場所の説明は受信仕様・出力に含まれていない。

## 利用者が確認する操作

```powershell
.\.venv\Scripts\python.exe scripts\measurement_probe.py
```

1. PCが表示するQRをスマホのカメラで読み、Safariでページを開く。
2. 屋内外、建物名または目印、詳細位置を入力する。
3. 「Get Location and Send」を押す。英語UIの表記は既存ページの規約に合わせる。
4. 不足・不正があれば英語の入力エラーを示す。この段階では測位・POSTしない。
5. 有効なら現在の入力を確定し、フォームを操作不可にして測位・送信する。
6. PCが座標と場所情報の両方を検証・受理し、従来どおりstatus:okを返す。
7. スマホはPCの受信成功を表示する。成功は場所情報も含めた受理確認であり、Speedtestの完了を意味しない。
8. PCがWi-Fi・Speedtestを取得し、場所情報を含む統合JSONを一度表示して終了する。

位置情報だけの受信コマンド `scripts/phone_location_probe.py` でも同じ必須検証を行い、三項目を含む受信データを表示する。単独受信は従来どおりCtrl+Cまで動く。一括取得の一件採用・自動終了とは区別する。

## 英語画面の仕様

既存の `lang="en"`、座標表示、状態メッセージ、権限拒否の案内を維持し、ボタンより前に一つのformと三つの入力欄を設ける。

| キー            | 英語の表示           | 入力部品・案内                                                                          |
| --------------- | -------------------- | --------------------------------------------------------------------------------------- |
| location_type   | Location Type        | select。初期値は未選択の「Select Inside or Outside」。選択肢Inside／Outside             |
| location_name   | Building or Landmark | 一行input。説明「Inside: building name. Outside: nearby place or landmark.」            |
| location_detail | Location Details     | 小さなtextarea。説明「Include the floor when applicable, and describe the exact spot.」 |

- 屋内外によってフォームを複雑に切り替えない。建物・階数リストや追加のfloor項目は作らない。
- 各欄へlabelを関連付け、required属性を付ける。例はplaceholderだけに依存せず説明文でも示す。
- 屋内外にinsideを勝手に初期選択しない。名前・詳細も空で始める。
- 入力欄はスマホ幅に収め、縦に並べる。既存ページに最小限のCSSを追加する。
- formのsubmitで処理し、既定のページ遷移をpreventDefaultで止める。Enterやボタン操作から同じ検証・送信経路を使う。textarea内の改行は入力として維持する。
- 不正入力では対象欄に英語の説明を出すかreportValidity等で示し、対象欄にフォーカスする。色だけで示さない。
- 形式・長さの検証後、getCurrentPositionを同じユーザー操作の処理から呼ぶ。権限状態の事前照会や、測位前の追加HTTP通信を挟まない。
- 測位開始前に三項目の値をローカルのオブジェクトへコピーし、その値を送る。測位完了時に変更後のDOMを読み直して別の場所情報と組み合わせない。
- 測位・送信中は入力欄とボタンを無効化し、二重操作を防ぐ。
- 測位段階で失敗したら入力内容を保ったまま再編集・再操作を可能にする。POST開始後は既存どおり再送を許可しない。
- 画面内での一時保持は許可するが、localStorage、sessionStorage、IndexedDB、Cookie、履歴用ファイル・DBへ保存しない。入力値をURLのクエリへ付けない。
- autocomplete="off"をフォームへ指定する。ブラウザー自身の履歴・自動入力・ページ復元を完全に禁止できる保証はせず、アプリとして過去値を保存・復元する機能を作らない。

## データ形式と検証

### POST

既存の送信先、トークン、Content-Type、取得座標・時刻を維持し、同じJSONに三項目を追加する。

```json
{
    "latitude": 40.42,
    "longitude": -86.91,
    "sent_at": "2026-11-09T12:00:00.000Z",
    "location_type": "inside",
    "location_name": "Example Hall",
    "location_detail": "2nd floor, beside the east window"
}
```

### 三項目の規則

| 項目            | 検証・正規化                                                          |
| --------------- | --------------------------------------------------------------------- |
| location_type   | JSON文字列でinsideかoutsideの完全一致。大文字・未知値・前後空白は拒否 |
| location_name   | JSON文字列。前後の空白を除去した後、1〜200文字                        |
| location_detail | JSON文字列。前後の空白を除去した後、1〜500文字                        |

- 文字列への自動変換はしない。数値、真偽値、null、配列、オブジェクトは拒否する。
- 名前・詳細は日本語などUnicodeも許可する。画面が英語であることと入力言語は区別する。
- 長さはUnicodeコードポイント数とし、PCではlen、JavaScriptではArray.from(value).length等で確認する。UTF-16コード単位を数えるmaxlengthだけに依存しない。
- 名前・詳細の内部の空白・改行は維持し、大文字小文字の統一、翻訳、Unicode正規化、長すぎる文字列の切り詰めは行わない。
- 名前・詳細のNUL文字は拒否する。HTML記号等を勝手に削除しない。画面へ値を挿入する場合はtextContent等を使い、innerHTMLへ連結しない。
- クライアント側の検証は操作補助であり、最終的な採用条件は必ずPython側でも検証する。
- floorを独立して検証しない。「階数が適用される場合は詳細へ入力」は利用者への案内とする。座標から階数・屋内外・建物名を推定しない。

## PC側の検証方針

既存のPOSTと `validate_location(data)` の引数構成を維持し、この関数で三項目を無条件に必須とする。方式選択、require_metadata、サーバーの必須性設定、旧形式へのフォールバックは追加しない。

1. 従来の座標・日時の必須検査と値の検証を維持し、その後location_type、location_name、location_detailの順に存在・型・値を検証する。最初のエラーで止める。
2. 六つの入力項目すべてが正常な場合だけ、正規化した辞書を返す。定義していないフィールドを返り値へコピーしない。
3. 新規項目の不足・型・値・長さの失敗はLocationErrorを使い、HTTP 400と `stage: "validation"`、`field`、英語の `error` を返す。座標のconversion等の既存仕様は変えない。
4. Handlerは検証完了後にreceived_atをPCで付与し、on_locationへ渡す。不正な場所情報では採用・応答完了コールバックを呼ばず、Wi-FiもSpeedtestも開始しない。
5. 場所情報三項目がない従来のJSONはHTTP 400とする。一部項目だけがある場合も拒否する。送信元やリクエスト内のsource・method等で検証を解除しない。

必須性は両入口と単独の検証関数で共通とし、クライアントがブラウザーかどうかの識別処理は追加しない。

正しい送信には従来どおりHTTP 200と `{"status": "ok"}` を返す。トークン照合、no-store、一件採用、重複409、応答処理完了後に計測を開始する動作は維持する。

## 統合JSONと失敗時の扱い

統合結果は、既存locationの四項目に次の三項目を加えた七項目とする。

```json
{
    "latitude": 40.42,
    "longitude": -86.91,
    "sent_at": "2026-11-09T12:00:00Z",
    "received_at": "2026-11-09T12:00:01Z",
    "location_type": "inside",
    "location_name": "Example Hall",
    "location_detail": "2nd floor, beside the east window"
}
```

上記はトップレベルの `location` の内容例であり、最終結果には従来どおり `wifi` と `speedtest` も含む。別のmetadataトップレベル、表示用の場所名連結、二つ目のJSON出力は追加しない。

LocationInboxは既存の辞書コピーを利用し、検証済み三項目を落とさず保持する。実装確認の結果、統合表示そのものの変更が不要なら不要なコード変更は行わない。JSONの非ASCII文字がエスケープされていても復号後の値が保持されていればよく、端末の文字コード設定を今回変更しない。

locationが四項目だけの成功結果は今後出力しない。nullや空文字による補完、場所情報のPC側対話入力も追加しない。

スマホの入力不正は測位前に示す。PC側で400になった場合は既存の「受け付けられなかった」表示とPOST後の再送禁止を維持し、PCの状況確認・必要時の再起動を促す。今回はエラー応答からフォームを再編集するプロトコルを新設しない。

入力中も既存の180秒の受信待ち期限を延長しない。測位の30秒、送信の15秒、PCの終了コード0・1・130、受信不明時の案内、計測失敗・後片付け失敗時に成功JSONを出さない仕様は維持する。

## 実装するテスト

### Pythonの入力検証・HTTP受信

- inside／outsideがそれぞれ成功し、名前・詳細の前後空白が除去される。
- 日本語、絵文字、内部空白・改行、HTML記号を保持し、表示言語を理由に拒否しない。
- 各項目の欠落、null、数値、真偽値、配列、オブジェクトを拒否する。
- location_typeの未知値・大文字・前後空白、名前・詳細の空文字・空白のみ・NULを拒否する。
- 名前200文字・詳細500文字は成功、各上限+1は失敗する。コードポイント単位で検証する。
- 三項目なしの旧形式と、一部項目だけを指定した入力は常に失敗する。関数の直接呼び出しでも必須条件が同じであることを確認する。
- HTTP POSTは三項目なしで400、正常な三項目付きなら200とstatus:okとなる。エラーはstage・field・理由を含む。
- 不正な場所情報ではon_locationとon_location_respondedを呼ばない。その後、期限内の正しいPOSTなら採用できる。
- 受信時刻の偽装や未知フィールドは結果へ入り込まず、定義済みの七項目だけを返す。
- 既存の認証、文字列座標、UTC変換、サイズ上限、GET配信、受信成功応答、409のテストを維持する。

### JavaScriptの動作

既存のtests/test_phone_location_web.pyにある、実HTMLのscriptをNode.jsのVMで実行する仕組みを必要範囲で拡張する。Node.jsを新規導入せず、未導入時は既存方針に従いスキップと記録する。

- 初期状態の屋内外が未選択で、空欄・空白のみ・上限超過の場合は測位もfetchも呼ばない。
- 正しい入力の後だけ測位し、POSTに確定した三項目・数値座標・送信準備時刻を含める。
- 測位待ち中にテスト側でDOMの値を変更しても、送信値は開始時の確定値のままとする。
- 連打・二重submitで並行測位・POSTを起こさない。測位失敗後は値を保持して編集・再操作できる。
- POST開始後・成功後は入力とボタンを無効にし、再送しない。成功はHTTP 200とstatus:okの両方で判定する。
- 既存のSafari権限拒否の案内と手動再操作のテストを、新しいformと操作部品に合わせて維持する。

VMのDOMモックではブラウザー固有のrequired検証・フォーカス・スマホ配置を完全には検証できない。HTML文字列にキーがあるだけのテストで入力機能を確認済みとせず、次節の実機確認を行う。

- 引数なしの一括取得で場所情報のないPOSTを拒否し、Wi-FiとSpeedtestを開始しない。
