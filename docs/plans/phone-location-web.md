# スマホのWebページによる位置情報取得・送信

## 状態

`completed`

状態は `draft`（作成・確認中）、`approved`（承認済み）、`completed`（実装・検証完了）で管理する。

PC側実装・自動テストと、利用者によるSafariでの正常動作確認が完了。利用者の指示に基づき状態を `completed` とする。PC側検証と実機確認を分け、個別に報告のない確認項目は検証記録に明記する。

## 目的と今回の範囲

既存のiPhoneショートカットに加え、スマホで開くWebページから位置情報を取得し、PCへ送信できるようにする。

ページはボタン一つを中心とした簡単な画面とし、「取得中」「送信中」「PCが位置情報を受理した」「失敗」をスマホで確認できればよい。通信性能の計測結果をスマホへ表示する機能は追加しない。Wi-Fi情報とSpeedtestを含む最終結果は、引き続きPCのターミナルだけに表示する。

今回の対象は位置情報を送る別の入口の追加に限定する。場所名・屋内外・階数の入力、選択肢、地図、履歴、SQLite保存、再試行機構、継続測位、結果照会API、PWA、利用者アカウントは追加しない。

README.md、既存計画書、AGENTS.md、依存関係は変更しない。今回の計画書作成では本ファイルだけを追加し、コード変更は実装担当が承認後に行う。

## 現状と基本方針

- `scripts/phone_location_probe.py` のHandlerが `POST /location?token=...` を受信し、座標・日時を検証してPCの受信時刻を付与する。
- `GET /location` は既存の疎通確認JSONを返す。この仕様は変えない。
- `scripts/cloudflare_tunnel.py` がトンネルを起動し、トークン付きPOST先URLとQRを表示する。
- `scripts/measurement_probe.py` は位置情報を一件受理し、HTTP応答処理完了後にWi-Fi取得・Speedtestを実行する。
- スマホへの `{"status": "ok"}` は位置情報の受理を意味する。計測全体の成功や保存完了ではない。

WebページとPOST先を同じPythonサーバー・同じCloudflare公開URLで提供する。既存のHTTPサーバーへ固定のページ配信経路を追加し、別のWebバックエンドや新規フレームワークは導入しない。これは利用者が希望したスマホのWeb入力経路を追加するための変更であり、計測・保存をクラウドへ移すものではない。

## 起動方式と互換性

### コマンド

一括取得の入口に `--location-method` を追加する。選択肢は `shortcut` と `web`、既定値は `shortcut` とする。

```powershell
# 既存の動作を維持
.\.venv\Scripts\python.exe scripts\measurement_probe.py

# スマホのブラウザーから位置情報を送信
.\.venv\Scripts\python.exe scripts\measurement_probe.py --location-method web
```

位置情報単独の受信コマンドにも同じ選択肢を追加する。Web送信の実機確認をSpeedtestなしで行えるようにする。

```powershell
.\.venv\Scripts\python.exe scripts\phone_location_probe.py --location-method web
```

Cloudflare単独起動のCLIにも同名の任意引数を追加する。引数なしの既存動作、`--token`、既存の停止・準備完了コールバックは維持する。不正な選択肢はサーバーやトンネルの起動前に引数エラーとする。

### URLとQR

| 選択方式         | QRが示すURL                                             | スマホ側の操作                         |
| ---------------- | ------------------------------------------------------- | -------------------------------------- |
| shortcut（既定） | `https://...trycloudflare.com/location?token=...`       | 従来のショートカット内でスキャン       |
| web              | `https://...trycloudflare.com/phone-location?token=...` | 通常のカメラでスキャンし、Safariで開く |

方式選択は案内とQRの遷移先を変えるもので、別の受信データ形式や認証方式を作るものではない。両方式とも既存POSTへ同じJSONを送信する。どちらかの方式から一件受理した後、もう一方から送られても、一括取得では既存の409により追加採用しない。

WebページのGETだけで位置情報の受理・計測開始・受信待ち期限の延長を行わない。QR表示後の180秒の受信待ちと、公開URL取得待ちの60秒は維持する。Webの取得・許可操作も180秒の中で行う。PCの受付が終了した場合は再起動して新しいQRを使う。

## 利用者が確認する動作

1. PCで `--location-method web` を指定して起動する。
2. PCは「スマホのカメラでQRを読み、ブラウザーで開いてください」と案内する。トークンの転記やURL入力は不要。
3. iPhoneのSafariで「位置情報をPCへ送信」というページが開く。
4. ページにはボタン「位置情報を取得して送信」と短い案内を表示する。ページを開いただけでは測位を開始しない。
5. ボタンを押すと位置情報アクセスを要求し、取得中の表示になる。必要に応じ利用者がOS・ブラウザーの許可を与える。
6. 座標を取得できたら、その座標をページに表示し、続けてPCへ送信する。別の送信ボタンは設けない。
7. PCのHTTP 200と `{"status": "ok"}` の両方を確認してから「PCが位置情報を受信しました。計測結果はPCで確認してください。完了まで同じ場所に留まってください。」と表示する。
8. PCは従来どおりWi-Fi情報取得、Speedtest、後片付けを実行し、最終JSONをターミナルへ一度表示して終了する。

ページは成功後に新たな通信を行わない。サーバーが終了しても表示済みの受信成功を消さない。計測完了の表示や、スマホが結果を受け取るまでサーバーを維持する処理は追加しない。

## Webページの仕様

### 表示と状態

- 英語の見出し、説明、操作ボタン、座標表示、状態メッセージのみとする。スマホ幅に対応するviewportを設定し、横スクロールを必要としない。
- 状態メッセージは `aria-live="polite"` 等で更新が伝わるようにする。色だけで成否を表現しない。
- 初期状態では「このスマホの現在地をPCへ送信します。PCの計測が終わるまで同じ場所に留まってください。」と表示する。
- ボタン押下時に直ちに無効化し、位置情報取得中・送信中・成功後は二重操作できないようにする。
- ページロード時のトークン欠落・重複・空値は送信不可とし、「PCで表示したQRから開き直してください」と表示する。トークンを画面へ表示しない。
- `window.isSecureContext` とGeolocation APIの利用可否を確認し、利用不可なら取得ボタンを無効にして説明する。外部から開く運用はCloudflareのHTTPS URLを前提とする。

### 測位とデータ

`navigator.geolocation.getCurrentPosition` を利用し、オプションは次の値に固定する。

- `enableHighAccuracy: true`
- `maximumAge: 0`
- `timeout: 30000`（ミリ秒）

高精度は要求であり、GPS使用や一定の精度を保証するものではない。ブラウザー・OSの位置情報許可と電波環境に依存する。継続測位・watchPositionは使わない。

取得できた緯度・経度が有限で範囲内かをJavaScript側でも確認する。画面にはAPIから取得した座標を文字列で表示し、POSTでは数値のまま送る。表示のための丸めで送信値を変更しない。

送信フィールドは既存と同じ三項目に限定する。

```json
{
    "latitude": 40.42,
    "longitude": -86.91,
    "sent_at": "2026-11-07T12:00:00.000Z"
}
```

`sent_at` は測位成功後、POST直前の `new Date().toISOString()` とする。GeolocationPosition.timestampは送信時刻として流用しない。PCのreceived_atは従来どおりPCが付与する。精度、標高、速度、方位、ブラウザーの識別情報、場所の説明は送らない。PC側の検証も引き続き適用する。

### POSTと成功判定

- ページURLのクエリからトークンを取得し、URL APIで同じオリジンの `/location?token=...` を構築する。クエリ中の任意の送信先URLは受け付けない。
- Content-Typeをapplication/jsonとして、既存POSTへ送る。Content-Lengthはブラウザーに任せ、手動設定しない。
- AbortControllerにより、POST開始から15秒で応答本文の受信・解析も含めて打ち切る。完了・失敗のどちらでもタイマーを解除する。
- HTTP 200であってもJSONとして読めない、またはstatusがokでなければ成功表示しない。HTTPエラーはfetch自体の例外と区別して確認する。
- 受信成功は位置情報の採用確認であり、Wi-Fi情報取得・Speedtest・永続保存の成功ではない。

### 失敗と再操作

| 状況                                            | スマホの表示・操作                                                                                   |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 位置情報の許可拒否                              | 許可が必要なことを表示。設定確認後に再操作できる                                                     |
| 位置を取得できない・測位30秒超過                | 取得失敗を表示し、再操作できる。PCにはPOSTしない                                                     |
| 不正な座標                                      | 取得値が不正と表示し、送信しない。再操作できる                                                       |
| HTTP 400・415等                                 | 送信を受け付けられなかったことを表示。自動再送せず、PC側の内容も確認するよう案内                     |
| HTTP 403                                        | 受付用URLが無効と表示し、新しいQRから開き直すよう案内                                                |
| HTTP 409                                        | すでに受理済み、または受付終了と表示。今回のPOST成功と断定しない                                     |
| 送信タイムアウト・通信切断・不正な成功応答・5xx | 「PCで受信を確認できませんでした。すでに受信している可能性があるため、PCを確認してください。」と表示 |

POST開始後に正常な受信確認が得られない場合は、そのページで再送ボタンを有効化しない。自動再送もしない。PCが受理済みである可能性があり、現在の一件採用方式と矛盾させないためである。やり直す場合はPCの状況を確認し、必要に応じ再起動して新しいQRを開く。

測位段階の失敗後は再操作できるが、受信待ち180秒の期限は延長しない。ページの再読み込みによる再送防止を永続管理する機能は追加せず、最終的な重複拒否は既存のPC側で行う。

## PC側のページ配信と互換性

- Handlerに `GET /phone-location?token=...` を追加する。POSTと同じトークン検査を使い、欠落・空・重複・不一致は403とする。検査処理の小さな共通関数化は可能だが、認証条件を変更しない。
- 成功時は `web/phone-location.html` をUTF-8のHTMLとして返す。ファイルパスは `__file__` 基準のプロジェクトルートから固定で解決する。作業ディレクトリに依存させない。
- URLのパスをそのままファイルパスへ変換しない。ディレクトリ一覧、任意ファイル配信、汎用的な静的ファイルサーバーは追加しない。
- HTMLにはトークンをPythonから埋め込まない。JavaScriptが現在のURLから読む。固定HTMLのためテンプレート展開は不要。
- HTML応答にはContent-Type（text/html; charset=utf-8）、バイト数で計算したContent-Length、Cache-Control: no-store、Referrer-Policy: no-referrerを設定する。
- 外部スクリプト、画像、フォント、解析サービスを使用しない。トークンをconsole、アクセスログ、HTML本文、計測結果、localStorage等へ保存・出力しない。利用者のURL履歴に残る可能性はあるため、起動ごとに変わる既存セッショントークンを維持する。
- POSTの成功・エラー応答にもCache-Control: no-storeを付ける。既存のステータスコード・JSON本文は維持する。
- GET /locationの既存疎通応答は維持する。未知のパスは404。HTMLが配置されていない・読み取れない場合は500とPC側のエラーを返し、トークンや内部パスをスマホへ露出させない。
- 同じオリジンへ送信するためCORS許可ヘッダー、OPTIONSの追加、別ポートのAPIは不要。

## トンネル・一括取得への組み込み

既存の `run_tunnel` に任意のキーワード引数 `location_method="shortcut"` を追加する。build_location_urlの既存仕様を維持し、Web用のURL生成は同じ公開URL・トークンの検証を再利用する小さな関数 `build_web_location_url` で行う。

- shortcutでは既存POST URL・案内・QR、webではWebページURL・カメラで開く案内・QRを表示する。
- 一度の起動で表示するQRは選択した方式の一つだけとする。トークンは既存と同じ一つを内部で渡す。
- 新しいキーワード引数を省略した関数呼び出し・単体CLIは従来動作を維持する。
- on_readyは従来どおりQR表示完了後に一度通知する。外部接続やページ読み込み完了を意味する通知へ変更しない。
- measurement_probeとphone_location_probeは選択した方式をrun_tunnelへ渡すだけとし、受理用コールバック・応答完了Event・Wi-Fi・Speedtest・停止処理を複製しない。
- 一括取得のJSON構造、各値、終了コード0・1・130、後片付け成功後にだけ最終結果を出す動作を維持する。
- 位置情報単独モードは既存どおりCtrl+Cまで連続受信する。Webページは一回の受信確認後にボタンを無効にするが、単独モードでページを開き直して送れば新たな受信として扱える。一括取得の一件制限と混同しない。

## 自動テスト

Python標準unittestと既存のモック・ローカルHTTPテストを使う。外部のOokla・Cloudflareへ接続しない。ブラウザーテスト基盤を新規導入しない。

### ページ配信・受信

- 正しいトークンのGETで200とHTML用Content-Type・正しいContent-Length・no-store・no-referrerを返す。
- トークンなし・空・誤り・重複・非ASCIIの不一致は403。HTML内容を返さない。
- 別作業ディレクトリでも固定HTMLを読める。未知のパス、ファイル名指定、パストラバーサル要求で他ファイルや一覧を返さない。
- HTML読込失敗は500とし、スマホ応答にファイルの絶対パス・例外詳細を含めない。
- ページGETではon_location・on_location_respondedを呼ばず、計測を開始しない。
- ブラウザー相当の数値座標・ISO 8601送信時刻をPOSTし、既存の正規化、受信時刻付与、200とstatus:okを確認する。
- GET /location、従来の文字列座標POST、トークン拒否、入力検証、409、応答完了コールバックの既存テストを維持する。

### 方式選択・統合

- 引数なしはshortcut、web指定はWebページURLをQR生成関数へ渡す。いずれも同じトークンを使う。
- build_location_urlは従来の結果のまま、build_web_location_urlは正しいパスとURLエンコード済みトークンを返す。未承認ホストや空トークンは拒否する。
- 各CLIの不正な選択肢を起動前に拒否する。既存のmainを直接呼ぶテストへテストランナーの引数が混入しないよう、argv指定・sys.argvのモック等を適切に使う。
- 両入口からrun_tunnelへ方式が渡り、既存の停止Event・on_ready・終了処理が維持される。
- ブラウザー相当のPOSTで、応答後にWi-FiとSpeedtestを一回取得し、結果はPC用の統合JSONだけになる。
- 異なるクライアント相当の同時POSTでも一括取得は一件採用、後続409。方式追加で採用上限や期限を変えない。
- 起動失敗、受信待ちタイムアウト、中断、計測失敗、後片付け失敗の既存検証を維持する。

HTMLの文字列に特定の関数名が含まれるだけのテストを、JavaScriptの動作確認の代わりにしない。今回の規模ではフロントエンドの実行確認を次節のSafari実機確認で行う。

## 実機でのページ動作確認

| 項目                   | 確認する動作                                                                                                |
| ---------------------- | ----------------------------------------------------------------------------------------------------------- |
| 正常系（必須）         | web指定で起動し、通常のカメラからSafariでページを開き、ボタン一つで測位・POSTできる                         |
| 受信確認（必須）       | APIで得た座標と送信中の状態が見え、200・status:okの後だけ「PCが受信」と表示する                             |
| 最終結果（必須）       | PCだけにlocation・wifi・speedtestが表示される。スマホは計測結果を要求せず、PC終了後も受信成功表示を維持する |
| 二重操作（必須）       | 連打しても測位・POSTが並行実行されず、成功後に再送できない                                                  |
| 許可拒否（必須）       | 許可しないと取得失敗の説明が出て、PCには採用されない。許可設定後に期限内なら再操作できる                    |
| 旧方式（必須）         | 引数なしで従来のQRを表示し、既存ショートカットを変更せず送信・統合取得できる                                |
| 取得不能・タイムアウト | 測位失敗や通信断を安全に再現できる範囲で確認し、成功と誤表示しない。POST後の不明状態ではPC確認を促す        |
| 権限・再起動           | トンネル再起動後は新しいURLで開く。公開ホスト変更時に再度許可が求められる場合があることを記録する           |

実機の正常系確認前に、ブラウザーの開発者ツール等で安全にAPIやfetchを差し替えられる環境があれば、403・409・500・不正JSON・通信タイムアウトの表示分岐も確認する。検証用の偽測位機能を製品HTMLへ追加しない。新しい依存関係を勝手に導入しない。

ブラウザーが返す座標は、ショートカットと同じ値になる保証はない。同じ実機・近い時刻・同じ場所で比較し、明らかな異常がないかを記録する。一定の誤差以内であることを今回の完成条件として新たに設定しない。

### Safariの位置情報拒否への対応

- 利用者環境：iOS 27.2。Safariのサイト別設定は許可済みだったが、iPhoneのプライバシーとセキュリティ側の位置情報設定が原因で拒否されていた。利用者がその設定を許可した後、期待どおりの動作を確認済み。
- 実装確認：ボタンのクリックから同期的にgetCurrentPositionを呼び出している。Permissions APIによる事前判定・早期拒否は元から行っていない。HTTPS確認も既存どおり。今回の症状を起こすコード上の直接原因は特定できていない。
- WebKitの[258726](https://bugs.webkit.org/show_bug.cgi?id=258726)・[275950](https://bugs.webkit.org/show_bug.cgi?id=275950)には、Permissions APIと実際のサイト別許可が一致しない報告がある。修正済みとされており、今回のiOS 27.2で同じ不具合が発生している証拠とは扱わない。権限状態の事前照会を取得可否の条件にしない方針を維持。
- [Appleの説明](https://support.apple.com/en-us/102647)に基づき、拒否時のページにOSの位置情報サービス・Safari Websitesとサイト別許可を分けた確認手順を追加。設定変更後の手動再操作・必要時の再読み込みを案内する。権限の自動変更・強制許可はできない。
- PermissionDeniedと同期的なSecurityError・NotAllowedErrorを権限エラーとして案内し、その他の取得開始失敗と区別する。自動再要求を行わず、POST開始後の再送禁止も維持。
- 既に導入済みのNode.jsのVMで実HTML内のJavaScriptを実行し、拒否時のPOST未実行・案内表示、手動再操作後の成功、成功後の二重送信防止を検証。新規依存の導入はない。これはSafariの実行や権限ダイアログの実機検証ではない。
- [Safari 27.2の公式変更一覧](https://webkit.org/blog/18515/webkit-features-for-safari-27-2/)では、本件と同一のGeolocation権限拒否についての記載を確認できなかった。今回の拒否は利用者によるOS側の設定変更で解消しており、Safariの不具合が原因だったとは扱わない。
